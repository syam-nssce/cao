Project Ideas and Student Work

The project ideas below are aligned with the four modules of the KTU Computer Organization and Architecture (PBCST404) syllabus. They are suitable for B.Tech students and can be implemented using simulation tools, programming, or hardware description languages. Each project lists its objective, what to implement, the expected outcome and useful resources. Projects may be chosen individually or in small groups, as the course requires.

Suggested Areas

  • Cache mapping and replacement-policy comparison.
  • Cache miss-rate analysis using different access patterns.
  • Pipeline hazard identification and mitigation.
  • Performance comparison of single-cycle and pipelined processor designs.
  • Virtual-memory address translation and TLB behaviour.
  • Simulation of programmed I/O, interrupt-driven I/O or DMA.

A. Beginner-level projects

These projects suit students who are new to processor architecture simulation. Most can be completed using Python, C, or RISC-V assembly.

1. RISC-V Assembly Programming Toolkit

Beginner   Syllabus coverage: Module 1 – RISC architecture, assembly language, instructions, addressing modes and programming concepts.

Objective: Develop a collection of RISC-V assembly programs to demonstrate how high-level programming tasks are executed at the processor level.

What students should implement:

  • Programs for arithmetic and logical operations.
  • Finding the largest and smallest elements in an array.
  • Sorting an array using bubble sort or selection sort.
  • Searching for an element using linear and binary search.
  • Programs using loops, conditional branches and functions.
  • Programs demonstrating stack operations and function calls.

Suggested extension: For selected C programs, compare the C source code with the generated RISC-V assembly. Identify how variables, loops, conditions and function calls are translated into instructions.

Expected outcome: A collection of tested RISC-V programs, with explanations of the instructions, registers, memory locations and addressing modes used.

Useful links:

  • RISC-V Assembly Programming – Learning Resources
  • RISC-V Assembly Learn Environment (ALE)
  • Ripes Simulator

2. Interactive Memory Organization and Endianness Visualizer

Beginner   Syllabus coverage: Module 1 – Memory map, memory organization and endianness.

Objective: Develop an interactive application that demonstrates how data is stored in computer memory and how different byte-ordering schemes represent the same data.

What students should implement:

  1. Allow users to enter a decimal or hexadecimal number.
  2. Convert the number into binary and hexadecimal representations.
  3. Display how the bytes are stored in consecutive memory locations.
  4. Demonstrate both little-endian and big-endian representations.
  5. Allow users to select different data sizes, such as 8-bit, 16-bit, 32-bit and 64-bit.
  6. Demonstrate how memory addresses change when data is accessed.

Example: For the 32-bit hexadecimal value 0x12345678:

Memory addressLittle-endianBig-endian
10007812
10015634
10023456
10031278

Expected outcome: A web-based or desktop visualizer that helps users understand byte ordering, memory addressing and data representation.

Useful links:

  • RISC-V ISA Specifications
  • Ripes Simulator

3. RISC-V Instruction Encoder and Decoder

Beginner to Intermediate   Syllabus coverage: Module 1 – Machine language, instruction formats and instruction execution.

Objective: Develop a tool that converts RISC-V assembly instructions into their corresponding machine-code representations and vice versa.

What students should implement:

  • Accept assembly instructions such as ADD, SUB, AND, OR, LW, SW and BEQ.
  • Identify the instruction type: R-type, I-type, S-type, B-type, U-type or J-type.
  • Extract opcode, destination register, source registers, function codes and immediate values.
  • Generate the corresponding 32-bit machine instruction.
  • Display the binary and hexadecimal representations.
  • Decode a given machine instruction into its assembly representation.

Suggested extension: Show the individual bit positions of each instruction field and visually explain how an instruction is encoded.

Expected outcome: A working RISC-V assembler/decoder demonstration tool with test cases for different instruction formats.

Useful links:

  • The RISC-V Instruction Set Manual
  • RISC-V Assembly Programming
  • Ripes Source Code and Documentation

B. Intermediate-level projects

These projects involve processor datapaths, pipelining, cache organization and performance evaluation. They are particularly relevant to Modules 2 and 3.

4. Design and Simulation of a Single-Cycle RISC-V Processor

Intermediate   Syllabus coverage: Module 2 – Single-cycle processor, datapath and control unit.

Objective: Design and simulate a simplified single-cycle RISC-V processor that can execute a selected set of instructions.

What students should implement:

  • Program Counter (PC).
  • Instruction memory.
  • Register file.
  • Arithmetic Logic Unit (ALU).
  • Main control unit.
  • Immediate generation unit.
  • Data memory.
  • Multiplexers and supporting datapath connections.

Suggested instruction set:

  • Arithmetic: ADD, SUB, ADDI
  • Logical: AND, OR
  • Memory: LW, SW
  • Branch: BEQ

Implementation approach:

  1. Design the processor datapath.
  2. Develop the control signals for each instruction.
  3. Integrate the datapath and control unit.
  4. Execute sample assembly programs.
  5. Observe register and memory changes.
  6. Verify the correctness of instruction execution.

Students can use Verilog or VHDL for hardware implementation, or a processor simulator for a software-based implementation.

Expected outcome: A working single-cycle processor model, supported by a datapath diagram, simulation waveforms and test results.

Useful links:

  • SonicRV – RISC-V Processor Simulator
  • QtRvSim User Manual
  • Nand2Tetris – Computer Architecture Project

5. Five-Stage RISC-V Pipeline Simulator with Hazard Detection

Intermediate   Syllabus coverage: Module 2 – Pipelined processor, pipeline hazards and hazard resolution.

Objective: Develop a simulator that demonstrates the execution of instructions through a five-stage processor pipeline.

The five stages to be modelled:

  1. IF – Instruction Fetch: Fetch the instruction from instruction memory.
  2. ID – Instruction Decode: Decode the instruction and read registers.
  3. EX – Execute: Perform the ALU operation or calculate an address.
  4. MEM – Memory Access: Read from or write to data memory.
  5. WB – Write Back: Store the result in the destination register.

What students should implement:

  • Display the five pipeline stages.
  • Show multiple instructions executing simultaneously.
  • Represent pipeline progress cycle by cycle.
  • Identify data hazards and control hazards.
  • Demonstrate forwarding and pipeline stalls.
  • Implement a basic hazard detection unit.
  • Compare execution with and without hazard-handling techniques.

Suggested experiment: Consider the following instructions:

ADD x5, x1, x2
SUB x6, x5, x3
AND x7, x6, x4
OR  x8, x7, x2

Students should identify the dependencies between instructions and demonstrate how forwarding can reduce stalls.

Performance analysis: Compare total clock cycles, number of stalls, number of completed instructions, CPI (Cycles Per Instruction) and execution time under the assumed clock period.

Expected outcome: An interactive pipeline visualization tool that demonstrates instruction execution, hazards, forwarding and performance improvement.

Useful links:

  • SonicRV – Pipeline Processor Visualization
  • QtRvSim – Processor Pipeline Simulation
  • Ripes – RISC-V Processor Simulator

6. Cache Memory Simulator: Mapping Techniques and Replacement Policies

Intermediate   Syllabus coverage: Module 3 – Cache memory, mapping techniques, replacement policies and cache performance.

Objective: Develop a cache simulator to study how different cache organizations affect memory-access performance.

What students should implement:

Part 1: Cache mapping techniques

  • Direct mapping.
  • Fully associative mapping.
  • Set-associative mapping.

Part 2: Replacement policies

  • Least Recently Used (LRU).
  • First-In First-Out (FIFO).
  • Random replacement.

Part 3: Cache parameters. Allow users to configure cache size, block size, number of cache lines, associativity and memory access sequence.

Part 4: Performance evaluation. For a given memory access sequence, calculate:

  • Cache hits and cache misses.
  • Hit ratio and miss ratio.
  • Number of memory accesses.
  • Average Memory Access Time (AMAT), using specified hit time and miss penalty assumptions.

Suggested experiment: Run the same memory access sequence using direct-mapped, fully associative and set-associative caches. Compare the hit and miss rates.

Expected outcome: A graphical cache simulator that enables users to understand cache mapping, replacement policies and the effect of cache configuration on performance.

Useful links:

  • Ripes – Cache Simulation Features
  • gem5 – Cache Configuration Tutorial
  • gem5 – Memory System Documentation
  • EDUCache – Educational Cache Simulator Research

7. Comparison of Cache Replacement Algorithms

Intermediate   Syllabus coverage: Module 3 – Cache replacement policies and cache performance.

Objective: Investigate the performance of different cache replacement algorithms using simulated memory-access patterns.

What students should implement:

  • FIFO replacement.
  • LRU replacement.
  • Random replacement.
  • Optional: Least Frequently Used (LFU).

Suggested experiments:

  1. Generate sequential memory accesses.
  2. Generate random memory accesses.
  3. Generate repeated accesses to a small set of addresses.
  4. Generate accesses with locality of reference.
  5. Run each sequence with different cache sizes.
  6. Compare the replacement algorithms.

Performance metrics:

  • Hit ratio and miss ratio.
  • Number of evictions.
  • Number of compulsory, capacity and conflict misses, where the simulator supports their classification.

Suggested extension: Allow users to upload a memory-access trace file and compare the performance of different replacement policies.

Expected outcome: A comparative study supported by graphs and experimental results explaining which replacement policy performs better under different workloads.

Useful links:

  • gem5 Documentation
  • gem5 Cache Configuration Tutorial
  • Ripes Simulator

8. Virtual Memory and TLB Performance Simulator

Intermediate   Syllabus coverage: Module 3 – Virtual memory, address translation, page tables, TLB and memory protection.

Objective: Develop an interactive application to demonstrate virtual-to-physical address translation and the role of the Translation Lookaside Buffer (TLB).

What students should implement:

  • Accept a virtual address.
  • Divide the address into page number and page offset.
  • Implement a page table.
  • Translate virtual addresses into physical addresses.
  • Implement a TLB to store recently used translations.
  • Identify TLB hits and misses.
  • Demonstrate page faults.
  • Show how page-table entries are updated.

Suggested experiment: Compare address translation (1) without a TLB, (2) with a TLB, (3) with different TLB sizes, and (4) with different memory-access patterns.

Performance analysis: TLB hit ratio, TLB miss ratio, number of page-table accesses, and Effective Memory Access Time under specified latency assumptions.

Expected outcome: A visual virtual-memory simulator that explains address translation and demonstrates how TLBs improve memory-access performance.

Useful links:

  • gem5 Documentation
  • gem5 Memory System
  • Ripes Simulator

C. Advanced-level projects

These projects combine processor architecture, hardware design, simulation and performance analysis. They suit students who are comfortable with programming and computer architecture fundamentals.

9. Design of a Multilevel Cache System and Performance Analysis

Advanced   Syllabus coverage: Module 3 – Multilevel cache organization and cache performance.

Objective: Design a simulation model of a memory hierarchy consisting of L1, L2 and optionally L3 caches.

What students should implement:

  • Separate L1 instruction and data caches.
  • Unified L2 cache.
  • Optional L3 cache.
  • Main memory.
  • Configurable cache sizes and associativity.
  • Cache hit and miss handling.
  • Data transfer between cache levels.

Suggested experiments:

  • Compare a single-level cache with a two-level cache.
  • Study the impact of L1 cache size.
  • Study the impact of L2 cache size.
  • Compare inclusive and exclusive cache organizations, if implemented.
  • Analyse the effect of block size on cache performance.

Performance metrics: L1 hit and miss rates, L2 hit and miss rates, Average Memory Access Time, total memory-access penalty, and performance under different workloads.

Expected outcome: A multilevel cache simulator and a detailed performance analysis showing how cache hierarchy improves memory performance.

Useful links:

  • gem5 Cache Configuration Tutorial
  • gem5 Memory System Documentation
  • gem5 Official Documentation

10. Performance Analysis of RISC-V Processor Architectures Using gem5

Advanced   Syllabus coverage: Module 2 – Processor performance; Module 3 – Memory systems.

Objective: Use the gem5 architecture simulator to investigate how processor and memory-system configurations influence application performance.

What students should implement:

  • Configure a basic processor model.
  • Select appropriate processor types supported by gem5.
  • Configure the cache hierarchy.
  • Select memory configurations.
  • Execute selected benchmark programs.
  • Collect simulation statistics.
  • Compare performance across different configurations.

Suggested experiments:

ExperimentConfiguration comparison
Processor performanceIn-order vs out-of-order models
Cache performanceSmall vs large L1 cache
Cache hierarchyL1 only vs L1 + L2
Memory performanceDifferent memory configurations
Workload analysisSorting vs matrix multiplication

Performance metrics: Instructions executed, simulation cycles and ticks, CPI (where the selected model and statistics permit its calculation), cache hit/miss statistics, and memory-access latency.

Expected outcome: A research-oriented comparative study of processor and memory-system configurations, supported by simulation results and graphs.

Useful links:

  • gem5 Official Documentation
  • gem5 Cache Configuration Tutorial
  • gem5 Memory System Documentation

Important: gem5 is more complex than Ripes or QtRvSim. Students should begin with the official introductory material and a simple configuration before attempting advanced processor comparisons. Some older sections of the gem5 learning documentation are explicitly marked as outdated.

11. Design and Simulation of a DMA-Based Data Transfer System

Advanced   Syllabus coverage: Module 4 – I/O organization, programmed I/O, interrupt-driven I/O and Direct Memory Access (DMA).

Objective: Develop a simulation model demonstrating how data can be transferred between an I/O device and main memory using different I/O techniques.

What students should implement: Model three data-transfer mechanisms.

A. Programmed I/O

  • CPU continuously checks the status of the I/O device.
  • CPU controls the data transfer.
  • Demonstrate the time spent by the CPU in polling.

B. Interrupt-driven I/O

  • I/O device generates an interrupt when it is ready.
  • CPU responds to the interrupt.
  • Demonstrate how the CPU can perform other tasks while waiting for the device.

C. Direct Memory Access (DMA)

  • CPU initializes the DMA controller.
  • DMA controller transfers data between the I/O device and memory.
  • CPU receives an interrupt after transfer completion.

Suggested experiments:

  • Transfer 100 bytes, 1 KB and 10 KB of data.
  • Compare CPU involvement in all three techniques.
  • Compare the total transfer time using assumed device and bus parameters.
  • Study the effect of increasing data-transfer size.

Expected outcome: A simulation application that visually demonstrates the three I/O techniques and compares their efficiency.

Useful links:

  • CPUlator – Processor and I/O Simulation
  • RISC-V Assembly Learn Environment
  • Ripes Simulator

12. RISC-V-Based Computer System Design Using HDL

Advanced   Syllabus coverage: Modules 1, 2 and 4 – RISC-V architecture, processor datapath, control unit and I/O organization.

Objective: Design a simplified RISC-V-based computer system by integrating a processor, memory and basic input/output peripherals.

What students should implement:

  • A simplified RISC-V processor.
  • Register file and ALU.
  • Instruction and data memory.
  • Control unit.
  • Memory-mapped I/O interface.
  • GPIO module.
  • LED and switch interface.
  • Basic serial communication interface, if feasible.

Suggested demonstration:

  • Read the status of input switches.
  • Perform arithmetic operations.
  • Display the result using LEDs.
  • Transfer data through a serial interface.
  • Demonstrate processor interaction with memory-mapped peripherals.

Implementation tools: Verilog or VHDL; an FPGA development board, if available; a RISC-V simulator for initial validation.

Expected outcome: A simplified computer system capable of executing selected RISC-V instructions and interacting with external peripherals.

Useful links:

  • Ripes Simulator
  • QtRvSim User Manual
  • RISC-V Specifications

Project submission requirements

To ensure that projects demonstrate actual learning rather than merely presenting an existing simulator, students should submit:

  1. Problem statement: The architectural concept being investigated.
  2. Design: Block diagram, flowchart or system architecture.
  3. Implementation: Source code, HDL files or simulation configuration.
  4. Test cases: At least five meaningful test cases.
  5. Experimental analysis: Results obtained by varying relevant parameters.
  6. Comparison: Graphs or tables explaining the observed performance.
  7. Demonstration: A working application or simulation.
  8. Report: Explanation of the architecture concepts demonstrated and conclusions.

Important guideline: Students should not simply operate Ripes, gem5 or another existing simulator and submit screenshots. They should implement a meaningful component, develop a simulation model, automate experiments or perform a systematic performance analysis.
